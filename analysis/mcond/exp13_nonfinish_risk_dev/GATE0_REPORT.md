### Gate 0A判定

**確定オッズを学習入力・統制変数へ使うことを禁止するユーザー指示を厳格に
適用すると、2023年development dataでは市場確率という特徴自体が構築
不可能**（正常完走馬・止馬のいずれでも0%）。これは選択バイアス型のFAIL
候補（止馬だけ低い場合）とは異なる、**カテゴリ全体の不在**という、より
重い制約である。

**この監査だけでは「FAIL」と断定しない**——ユーザーの元の設計（S1=S0+
時点安全なv6確率+市場確率）が2023年で実行不能であることを示す事実確認に
留め、対応方針（例: 市場確率を含む変種は2023年では評価せず、v6確率と
その他の統制変数のみで判定する／該当特徴を持つ変種のGate評価自体を
2026年以降の新規収集データが十分蓄積されてから行う、等）はユーザー判断に
委ねる。**確定オッズを代用することは行わない**（明示的に禁止されているため）。

## Gate 0B: 全出走馬特徴の再構築（アーキテクチャ検証、raw score一致の実測は未実施）

### 確認できたこと（実装コード読解による、コードは変更していない）

1. **`build_dataset.py`の非完走行除去は1箇所のみ**: `dropna(subset=["着順"])`
   （328行付近）。この直前でjoinされる4つの基盤raw CSV
   （`lgbm_20130105-20251228.csv`/`cat_20130105-20251228.csv`/
   `torch_transformer_20130105-20251228.csv`/`add_20130105-20251228.csv`）は
   **いずれも非完走行を含んだ状態でJOINされている**ことを実測で確認した
   （JOIN後行数631,965 = dropna後行数626,774 + 除去件数5,191 = 止2,946+
   外1,212+消1,007+丸数字26+不明0、EXP10の実測と一致）。すなわち**`止`馬の
   基本情報（場所・距離・クラス・前走成績等の前走系特徴を含む）は
   dropna直前まで一切失われていない**。
2. **正常完走馬と止馬は同じfeature builderを通る（dropna前まで）**: 上記の
   通り、`convert_finish()`による着順の数値化と`dropna`は独立した処理で
   あり、それ以外の全JOIN・特徴計算（`add_rolling_stats`・
   `add_horse_rolling_stats`・`add_pace_features`）は**着順の値に一切依存
   しないロジック**であることをコードで確認した（`前1角`〜`前4角`等の
   "前走"接頭辞列を使うのみで、今走の結果列を参照する箇所はコード上
   存在しない＝結果列を特徴生成に使っていないことを確認）。
3. **v6の120特徴は自身がオッズ・人気を一切含まない**（`models/
   unified_rank_v6.pkl`の`feature_cols`を実際に読み込んで確認、120列
   全てが場所・距離・前走系・血統・騎手調教師コード・ローリング成績・
   kako5系・調教データ等の予測時点特徴のみ）。Gate 0Aの市場確率問題は
   v6のraw score自体には影響しない。
4. **kako5/course/jockey統計は識別子(血統登録番号)+日付キーのas-of集計**
   （`parse_kako5.py`・`build_master_v2.py`の`compute_history_features()`を
   実装コードで確認）であり、**「今回のレースが完走したか」に依存しない
   ロジック**——原理的には止馬にも同じ関数を適用できる設計になっている。
5. **本番の週次スコアリング経路（`predict_weekly.py`の`parse_csv`→
   `export_marks_json.export_race`）自体が「まだ結果の出ていない馬」を
   毎週スコアリングしている**——これはGate 0Bが要求する「予測時点だけで
   構築された特徴でv6をスコアする」という操作と構造的に同一であり、
   本番で実績のある経路である。

### 未実施（実測のraw score一致照合ができていない理由）

上記1-5は全て**コード読解による構造的な実現可能性の確認**であり、
ユーザーが要求する「**正常完走馬について、新しい全starter pipelineの
raw v6 scoreが既存master_v2経路と一致するかを事前固定した許容誤差で
照合する**」という**数値実測**はまだ行っていない。理由:

- `kako5_*`・`hist_same_cond_*`・`prev_hosei`・`trnH_*`・`trnW_*`・
  `course_n_prev`等、v6の120特徴の過半数は`build_dataset.py`単体ではなく
  後続の`parse_kako5.py`・`build_master_v2.py`（坂路/WC調教データ、補正
  タイムCSV等、複数の大容量外部ファイルとのJOINを含む）で構築される。
  これらを「止馬を含めた全starter」向けに再実行するには、各スクリプトの
  入力を`dropna`前の行集合に差し替えた上で、既存の大容量結合処理
  （坂路5,377,807行・WC 765,901行等、CLAUDE.md記載）を再実行する必要が
  あり、単発の検証としては相応の実行時間を要する。
- 拙速に数値を出して「一致した」と報告することは、ユーザーが明示的に
  警戒している「陽性数不足を結果操作でごまかす」のと同種の誤りになり
  うる（今回は方向が逆だが、検証プロセスの手抜きという点で同じ問題）。
  **確実でない数値を確実であるかのように報告しない**ため、本Gate 0報告
  では実測を保留する。

### Gate 0B判定

**アーキテクチャ上は実現可能と判断する（上記1-5の根拠）が、raw score
一致の実測照合という必須条件はまだ満たしていない。Gate 0Bは「暫定PASS
（アーキテクチャ検証のみ）、数値照合はStage1着手直後の最初のタスクとして
実施する」と報告する**。ユーザーがこの状態でのStage1続行を許可するか、
数値照合の完了を待つかは判断を仰ぐ。

### Power analysis

**候補特徴数に対する Events Per Variable (EPV) ヒューリスティック**
（Peduzzi et al. 1996、ロジスティック回帰の安定推定に必要な最低目安
EPV≥10、理想はEPV≥20）:

- S2（v6確率+市場確率+人気+出走回数+休養日数、Gate 0A制約下では市場確率
  抜きで実質3-4特徴）: EPV = 145/4 ≈ **36**（十分）
- S4（S2+過去非完走履歴+履歴変動+大敗頻度+馬体重履歴、推定10-15特徴）:
  EPV = 145/13 ≈ **11**（目安の下限付近、理想の20には届かない）

**2023年単独では、S4のように特徴数を増やした変種の安定推定は境界線上**。
[[project_exp10_downside_risk]]のStage1.5も同程度の陽性数規模（年間
150-260件）で「meeting-day bootstrap CIがゼロを跨ぐ」というFAILに至って
おり、EXP13のS4も同型のリスクを負っている可能性が高い（構造的な参考、
実測ではない）。

**厳密な「予測したい改善幅」に対する検出力計算**（EXP05-Fの
`POWER_ANALYSIS.md`と同じ様式のz検定ベース公式）は、S4対S2のlogloss/
PR-AUC差の典型的な効果量に関する事前情報（パイロットデータ）が無いため
実行できない——**これ自体がGate 0Dの結論の一部**:145件という陽性数では、
効果量事前推定なしに検出力を保証できる根拠がない。

### Gate 0D判定

**2023年単独でのS4 vs S2判定は、EPVヒューリスティック上「境界線上」であり
確実にPASSとは言えない**。障害・取消を混ぜて陽性数を増やすことは
ユーザー指示により行わない。判定は以下のいずれかをユーザーに提案する
（決定はユーザーに委ねる、本報告では選択しない）:
1. S4の特徴数をさらに絞り込みEPVを改善した上でGate評価する
2. 2023年単独でなく2013-2022年も含めた学習期間内でのGate2相当比較に
   留め、2023年developmentでの最終判定はS2のような少数特徴の変種に限定する
3. データ不足を理由にEXP13をここで一旦終了する
