# EXP07 共同損益分布の監査(§6) / Gate J0

**実施日**: 2026-09-20　**方式**: read-only設計＋合成データ(乱数スコア)による自己整合性検証のみ。
実レースデータは一切使っていない（Stage 0完了後、Stage 2A[実データ]着手前の合成検証段階）。

---

## 設計方針

新しい確率モデルは作らない（仕様書4節）。既存の厳密PL連鎖実装`pl_probs.py`
（結合版仕様書Vol.III記載、本番`pl_probs.py`）が既に単勝〜三連単の閉形式確率関数を
持っているため、これを土台に**1-2-3着の順列(i,j,k)を1状態とする共同状態空間**を構築する
（`build_scenarios.py`）。全ての標準券種（単勝・複勝・馬連・ワイド・馬単・三連複・三連単）は
1-3着の情報だけで的中判定できるため、この状態空間で券種横断の共通payoffベクトルを表現できる。
18頭立てで状態数は最大4,896（`docs/plans/exhaustive_betting_policy_verdict_20260825.md`が
引用する数値と一致）。

各状態の確率は`pl_probs.p_sanrentan(w,i,j,k)`をそのまま使う。近似なし、結果ラベル（着順・払戻）
への参照はコード全体でゼロ（`build_scenarios.py`は`import`文からして本番モデル・結果データへの
依存を持たない）。

## Gate J0 検証項目と結果

| 検証項目 | 実装 | 結果(n=5,10,18頭、乱数シード20260920) |
|---|---|---|
| 確率が0〜1 | `probabilities_in_0_1` | **PASS**（全て`true`） |
| 排他的シナリオ確率和が1 | `probabilities_sum_to_1` | **PASS**（誤差<1e-6） |
| 同一馬の重複着順がない | `no_duplicate_horse_in_state` | **PASS**（`permutations`列挙により構造的に保証） |
| marginalを再集計すると元確率と一致 | `marginal_consistency`（単勝・複勝・馬連・馬単・ワイドの5種を直接計算値`pl_probs.p_*`と突合） | **PASS**（最大誤差は機械精度オーダー、n=18頭で全て1e-16オーダー、詳細は下表） |
| 馬券的中条件が実決済ルールと一致 | `ticket_wins_in_state()`、`test_build_scenarios.py`の12ユニットテスト | **PASS**（全14テスト通過、2026-09-20実行確認） |
| 結果情報をシナリオ確率作成に使っていない | コード監査（`build_scenarios.py`に着順・払戻列への参照ゼロ） | **PASS** |

### marginal誤差（n=18頭、状態数4,896、乱数シード20260920）

| 券種 | 最大絶対誤差 |
|---|---|
| 単勝 | 1.67e-16 |
| 複勝 | 1.67e-16 |
| 馬連（153ペア全チェック） | 8.33e-17 |
| 馬単 | 4.16e-17 |
| ワイド | 5.55e-17 |

いずれも機械精度（float64のULPオーダー）であり、統計的な誤差ではなく浮動小数点丸め誤差の範囲。
**共同状態空間の構築は数学的に厳密**（pl_probs.pyの周辺確率と完全に整合）と確認した。

## Gate J0 総合判定: **PASS**

共同着順分布は時点安全に（結果ラベル不使用で）構築可能であり、券種間の確率整合性（marginal
consistency）も機械精度で成立することを確認した。仕様書6節の停止条件
「共同着順分布が構築不能な場合、独立近似で本評価を行わない」には該当せず、Stage 1（合成データでの
ポートフォリオ最適化テスト）およびStage 2A（実データ評価）へ進んで良い。

## 既知の制約（設計時点で明記）

- 状態空間は1-3着の順列のみを対象とする。4着以降の情報は含まない（標準的な単勝〜三連単の
  決済には不要なため、これはスコープ内の単純化であり欠陥ではない）。
- `w`（PL重み）は呼び出し側（v6モデルスコア等）が渡す前提。この監査自体はモデルの予測精度を
  検証するものではなく、**与えられたモデルスコアから券種横断で整合した同時確率を作れるか**
  という構造的な健全性のみを検証している。
- 実際のレースでの構築（Stage 2A）では、出走頭数の変動（取消による頭数減少）、オッズ欠損、
  価格下振れ（odds_floorの保守化）等の実務的な処理が別途必要になる。これらはStage 1の合成
  テストで個別にカバーする。
