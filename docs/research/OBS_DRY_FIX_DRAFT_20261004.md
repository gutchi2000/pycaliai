## 0. 判定の要約（10/03）

正式判定は CONTRACT_NOT_MET（exit 4）。理由 3 系統のうち 2 つは監査側の範囲・期待値の誤りで、
収集の実欠陥ではない（Dry の T−2・三連複・final_rt の取得 276 件は rc 0・race_key・長さ・parser とも全て正常）。

## 1. 修正案

### F1. Dry 監査の保存先の範囲（監査側）
- 現状: `--dry` で forward store と journal の**両方**を `*_dry` に切り替える（`analysis/obs_stage0_audit.py:476-478`）。
  必須 stage の `t10`・`close_late` は本番 T-10 経路だけが書くので（`:81`）、Dry では必ず 23/23 欠損（`task_not_fired`）と出る。
- 案: `--dry` のときは「Dry が収集する stage（t2_candidate / trio_t10 / final_*）は dry の保存先、本番経路の stage（t10 / close_late）は本番の保存先」
  から読む。report に stage ごとの読込み元（`store`）を記録する。並走の重なり相手の journal も dry と本番の和にする（Dry 日の本当の並走を見るため）。
- 10/03 の和で再計算した参考値: t10・close_late は 23/23 取得、欠損 0（`supplement_20261003.json`）。

### F2. 被覆の期待値（発走前の出走頭数欄が 0）
- 現状: 発売中の組数の期待値を録の「出走頭数」欄から作る（`jv_records.py:153-164 _expected`）。発走前の中間オッズ（区分 1）では
  この欄が全録で 0 なので、期待値 0 → `complete=False`・`cap.ok=False`。被覆不一致 100%、並走成功率も 0 と出る。
  三連複 collector のスナップショット `ok`（`jvlink_trio_odds.py:455-467` の `slot_count_match`）も同じ理由で全件 false。
- 案: 出走頭数欄が 0（発走前）のときは「登録頭数 − 取消による未発売 filler」を期待値にする。確定後（区分 4）は出走頭数欄を使う。
- 枠連: 8 頭以下は発売されない（10/03 京都 9R `hatsubai_wakuren='0'`）。`wakuren_slot_count`（`jv_records.py:65-71`）は 8 頭でも 28 を期待する。
  発売フラグが 0 のときは期待値 0 にする。

### F3. 並走の成否を被覆の式から切り離す
- 現状: 並走の成否 = rc 0 ∧ 録あり ∧ `cap.ok`（`analysis/obs_stage0_audit.py:178-179`）。`cap.ok` が F2 の誤った被覆に依存する。
- 案: 並走の成否は「rc 0・race_key 一致・録長一致・malformed 0・（枠連以外で）発売数 = 登録頭数からの期待値」とし、被覆の合否は契約側だけで見る。
  10/03 の和でこの定義に直すと単独 120/120、重なり 519/521（`supplement_20261003.json`）。
- 併記: 現行の「±30 秒以内」は、final_rt 終了 1.2 秒後に始まる STOCK のような**逐次**の取得も重なりに数える。区間の交差（同時取得）でも数えて併記するか、
  計画 §3(6) の定義のままにするかは判断事項。

### F4. final_stock（蓄積系 O1〜O5）の取得時期
- 観測: 10/03 18:30 の FINAL で STOCK セッションは rc 0 だが O1〜O5 は 0 件。過去の蓄積系 O5 576 件はデータ作成日が全て開催週末の**翌月曜**（傍証）。
- 現状の予定: REFETCH は「開催日の翌日 20:00」（`obs_schedule.ps1:139-140`）。土曜分は日曜 20:00（月曜配信より前）、月曜の REFETCH は
  `--also-previous` なしで日曜分だけに絞る（`jvlink_obs.py:207-216`・`obs_schedule.ps1:72-73`）。**土曜分の final_stock を取る機会が無い**可能性。
- 案: 蓄積系の取得は月曜の配信後（例: 月曜 20:00 以降）に、対象日（土・日）を明示して 1 回行う。監査は final_stock をその後で評価する
  （Stage 0 の 2 開催日の判定は火曜以降）。月曜 20:00 時点で配信済みかは未確認なので、最初の週は取得結果で確かめる。

### F5. 記録・終了コード（記録系の欠陥）
- STOCK の journal に読込み総数・種別ごとの件数・`download_count` が無い（`jv_journal.write_event` が書かない）。「0 件」が未配信か絞り込みの結果かを区別できない。
  → STOCK 用に `n_records_read`・`by_kind`・`download_count` を記録する。
- `obs_schedule.ps1` の `Invoke-Py32`（`:45-48`）は `& py ...` を関数内で実行するので、Python の標準出力が戻り値に混ざり、transcript に残らない。
  `-Final` の `$c1 -ne 0`（`:68`）は配列との比較になり終了コードの意味が崩れる。→ 出力は `Out-Host`/ログへ、戻り値は `$LASTEXITCODE` だけにする。

### F6. 三連複 collector の Dry 分離漏れ（実欠陥）
- 現状: manifest の置き場所が固定（`jvlink_trio_odds.py:55 MANIFEST = OUT_DIR / "manifest.jsonl"`、書込み `:292` / `:417` / `:488`）。
  `--dry` でも raw・snapshot・forward ミラーは `_dry` に分かれるが、**git 追跡下の manifest にだけ Dry の行が追記される**。
- 証跡（`docs/research/obs_dry_audit/*/trio_manifest/`）: 既存 582 行は不変（最終コミット `5557fa69` の blob が現在のファイルの完全な先頭部分）。
  10/03 の追記 69 行（23 レース × raw 0B35・raw 0B31・snapshot）、10/04 も同形で追記。参照先は全て `_dry` 配下、raw ファイル 78 件の sha256 は記録と一致。
- 案: `--dry` のときは `manifest_dry.jsonl`（または `_dry/` 配下）へ書く。既に追記された行は**削除・巻き戻ししない**（証跡として保持）。
  追跡ファイルの差分の扱い（コミットするか、Dry 行を別ファイルへ写して元を戻すか）は判断事項。
- 付記: 週次フローの `git pull --rebase --autostash` はこの未コミット差分も stash して戻す（9/27 の autostash 事故と同じ経路を通る）。
  自動コミットは特定パスのみで、この manifest は取り込まれない（`git add -A` は HF の staging clone だけ）。

## 1b. 10/04 Dry で新たに分かったこと（`docs/research/obs_dry_audit/20261004/RUN_RECORD_20261004.md`）

- 正式判定は CONTRACT_NOT_MET（exit 4）。理由は 10/03 と同じ系統（F1・F2）に加えて、FINAL の強制終了による欠損がある。
- **FINAL の強制終了**
  - 18:30:01 に開始し、FINAL_RT を 13/23R 取り終えた 18:30:16.7 より後に終了コード `0xC000013A`（console への Ctrl+C か close）で止まった。transcript に終了の行は無い。
  - FINAL_RT の残り 10R と STOCK は実行されなかった。そのため final_stock の月曜配信仮説（F4）は 10/04 では検証できていない。
  - 同じコードで本番 T-10 の東京 8R（13:50）も起動直後に止まっていて、このレースの本番 T-10 価格は無い。
  - 原因は未確定。Interactive のタスクは開催中に毎回ウィンドウを出すので、閉じられると止まる。
  - 案 F7: 観測タスクと T-10 タスクを、ウィンドウを出さない形で起動する（例: `-WindowStyle Hidden`、または conhost を出さない起動器）。終了コードを journal か ledger に残し、FINAL が途中で止まったら翌日の REFETCH で取り直す。本番 T-10 の起動形式に触れるので Fable の判断が要る。
- **F5 の影響が実際に出た**: FINAL の Python 出力が transcript に残らない（`Invoke-Py32`）。どこまで進んで止まったかは journal から復元するしかなかった。
- **並走（F3 案の定義、和の保存先）**: 単独 170/180（94.4%）、重なり 392/406（96.6%）。
  - 重なりの失敗 14 件は本番 t20・t10 と体重 collector・exp05fs の重なりで、内容は発売数と登録頭数の不一致。取消が原因かは B3 で検証する。
  - 単独の失敗 10 件も同じ式によるものかを、あわせて確かめる。
- T−2 と別レースの本番 T−10 の重なりは 0 件（最小間隔 419.7 秒）。TRIO は同じレースの本番 T−10 と毎回重なる（176 組）。設計どおりで、別レースとの重なりは 0。
- 監査の二重実行（実行部の不備）: ledger に 10/04 の行が 2 行ある（generated_at 以外は同一）。削除せず残す。
  - 案: `obs_stage0_audit` が同じ (dates, dry, code_head) の行を書く前に既存行を検出し、`rerun_of` を付ける。
