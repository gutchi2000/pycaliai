# v7 候補: AI に JRDB の過去走特徴を組み込む (2026-11-13)

ユーザー「AI に組み込んで」。AI の見落としの順位表 (`FEATURE_GAP_SCAN_20261113.md`) で上位だった
前走のスピード指数・上がり/テン指数・位置取り補正・不利を、本番 v6 と同じ作り方のモデルに特徴として足した。

## 0. 状態

- **候補モデル v7 を作り、配信経路 (出走表 → bundle) まで通した。本番 (v6) は切り替えていない。**
- 毎週土曜朝の Phase A が、本番と同じ出走表から v7 の bundle を別フォルダ (`reports/shadow_v7/`) に作る。公開・買い目・本線には触れない。
- 切替に必要な残作業と、ユーザー判断が要る点は §5。

## 1. 何を足したか

`jrdb_features.py` (59 列、接頭辞 `j1_`)。JRDB 成績データ (SED) から、各馬の **5 日以上前の走** だけを使う。

- 1〜3 走前それぞれの: IDM (スピード指数)、素点、不利 (前・中・後・全体)、出遅、位置取り補正、コース取り、4 角コース取り、上昇度、
  テン指数、上がり指数、ペース指数、レースペース指数、馬体・気配コード、馬とレースのペース区分
- 近 5 走の IDM 平均・最大

学習 (master_v2 の全行) と配信 (出走表の各馬) で同じ関数を通す。独立に作った前走値との一致 100%、
配信相当 (その日の成績がまだ無い状態) でも同じ値になることを確認。テスト `tests/test_jrdb_features.py` (10 本)。

## 2. 学習 (`train_v7_jrdb.py`)

ラベル・学習窓 (〜2022)・重み・ハイパーパラメータ・回数 (515)・エンコーダ・seed は本番 v6 の bundle からそのまま引き、**特徴だけ** 追加。
同じコードで 120 特徴のまま再学習すると本番 v6 と ◎ が 100% 一致 (= 作り方を正しく再現できている)。

test 2024-25 (6,909R):

| seed | v6 再学習 ◎3着内 | v7 ◎3着内 | 差 [95% CI] | ◎1着の差 |
|---|---|---|---|---|
| 42 (保存したモデル) | 61.50% | 62.01% | +0.51pt [−0.31, +1.32] | +0.39pt |
| 1 | 61.54% | 62.54% | +1.00pt [+0.09, +1.94] | +0.77pt |
| 7 | 61.25% | 62.86% | +1.61pt [+0.72, +2.46] | +1.68pt |

平均 +1.0pt。11/12 の A/B (+1.10pt) と同じ大きさ。JRDB 特徴は gain の 15.8% を占める (最上位は近 5 走 IDM 平均)。

見落としが埋まったか (2023-25、同じ AI 順位の馬の平均に対する 3 着内の比。1 が理想):

| 前走の条件 | v6 | v7 |
|---|---|---|
| 直線の不利 ≥2 | 1.39 | 1.12 |
| 不利 (前/中/後) ≥2 | 1.23 | 1.12 |
| 不利 + 出遅 合計 ≥2 | 1.14 | 1.06 |
| 人気を裏切って大敗 + 不利 ≥2 | 1.26 | 1.11 |
| 前走 IDM 18 以下 | 0.75 | 0.78 |

不利まわりの過小評価は半分以下に縮んだ。前走 IDM 最低帯の過大評価はこの物差しではほとんど動いていない (下位人気帯は順位だけでは測りにくい)。

## 3. 配信経路

- `serve_history_feats.py`: 馬同定 (hit) の血統登録番号を `_serve_ped_id` 列に出す。
- `export_weekly_marks.py`: bundle に `jrdb_mode` があるモデルのときだけ JRDB 特徴を作る。2026 年に初出走した馬は履歴側が仮番号なので、
  **同定が hit の行に限り** 馬名で引き直す (対象レースより前に初出走し、約 3 年以内に走っている馬だけ。名前だけの引き直しは登録番号と 100% 一致)。
  成績ファイルが 9 日より古い / 前走の埋まりが 50% 未満なら bundle を不合格にする。
- 2026-11-08 の出走表で実行: 477 頭中 396 頭同定、前走あり 82% (学習時 87%)。
- `scripts/jrdb_refresh.py`: 今年ぶんの SED を取り直して `sed.parquet` を更新。既存タスク `PyCaLiAI_JRDB_Snapshot` (金土 19:40・土日 07:30) の後ろで自動実行。
- 較正器・払戻カーブ・クラス別経験率: `run_v7_pipeline.py` → `pl_calibrators_v7.pkl` / `pl_payout_curve_v7.pkl` / `class_prior_v7.json`。

**規約対応**: JRDB のデータ・指数は加工しても公開できない。`j1_` で始まる特徴は、根拠表示 (bundle の `why[]`) にもサイトにも出さない
(`marks_shap.py` と `build_site.py` の両方で除外、テストあり)。候補の成果物と紙上 bundle は git 管理外。

**運用を止めないための仕組み**
- 土曜朝に v7 で bundle が作れなかった日 (JRDB 成績が 9 日超古い、埋まり 50% 未満、モデルが無い 等) は、`weekly_nicegui.ps1` がその日だけ v6 で作り直す。失敗理由は Discord に出る。
- 戻すのは 1 コマンド: `python scripts/switch_production_model.py --to v6 --start <次の開催日>`。状態確認は `--status`。
- `artifact_pins.json` は v7 と v6 の両方を照合する。
- 紙上の比較は継続: 本番でない方 (v6) を `reports/shadow_v6/` に毎週作る (CW-15)。

**公開リポジトリとの関係**: GitHub の `gutchi2000/pycaliai` は公開設定。JRDB で学習したモデル・較正器・払戻カーブ・紙上 bundle は git に入れない
(`.gitignore`、このマシンにのみ存在、控え `models/production_backup/20261113_v7/`)。登録するのは照合用のハッシュだけ。
= **本番を動かせるのはこのマシンだけ**。別のマシンでは v7 の照合が通らず T-10 は止まる (v6 に戻せば動く)。

**切替時の確認** (2026-11-08 の出走表、本番の既定設定)
