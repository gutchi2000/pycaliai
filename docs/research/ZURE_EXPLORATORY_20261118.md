## A. PW の正体

### A1. 定義・計算式・入力・タイミング（`power_rating.py`）

- **何か**: 全レースの着順だけで逐次更新する多頭数 Elo。**芝とダートは別々のレーティング**。
- **更新式**: 1 レースで、馬 i の実績 s_i = 同じレースの各馬 j に先着なら 1、同着なら 0.5、負けなら 0 の合計。期待 e_i = Σ_j 1/(1+10^((R_j−R_i)/400))。
  R_i ← R_i + K(n_i) × √(頭数−1) × (s_i − e_i)/(頭数−1)。
  K(n) = 32 + (128−32)·exp(−n/6)（出走数 n とともに 128 → 32 へ減衰。既定 k0=128、floor_ratio=0.25、tau=6）。
- **初期値**: その芝ダが初めての馬は、同じレースで 3 走以上している馬の平均から始める。3 頭未満ならクラスごとの固定値（新馬・未勝利 1400、1勝 1500、…、G1 1850）。**新馬戦は全頭が同じ初期値になる**（第 1 段階で見つけた「全頭同率 1 位」の原因）。
- **スコア**: score = 100 × (R − R_lo)/(R_hi − R_lo)。R_hi = 現役最上位、R_lo = 現役の下位 1% 点（芝・ダートそれぞれ）。現役 = その芝ダで 1 年以内に出走・3 走以上・登録抹消されていない。
- **入力**: `data/master_v2_*.csv`（2013〜2025 の着順）、`data/kekka/{date}.csv`（2026 の着順）、`data/weekly/{date}.csv`（クラス名・芝ダ）。**オッズ・人気・走破タイム・JRDB は使わない。**
- **タイミング**: `weekly_nicegui.ps1` の `Invoke-PowerRating` が、Phase A（土曜朝）で `build --until {土曜の日付}`、Phase C（日曜夜）で `build`（全期間を作り直す）を回す。出力は `reports/power_rating/`（git 管理外）。
- **サイトに出る値**（`build_site.py power_score()`）: 結果のある開催日は `history.csv` の「そのレース前のレーティング」を、その時点のスケールで点にした値。まだ走っていない日は `ratings.csv`（最新）の値。

### A2. v8 の 220 特徴に PW は含まれるか

- **PW そのもの、または Elo/レーティング型の量は含まれない。** 本番の v6（120）・v7（179）・v8（220）の `feature_cols` を確認した。
- **PW の入力（過去の着順）は、生の形で含まれる**: 前走確定着順、前走着差タイム、prev_pos_rel、kako5_avg_pos / std_pos / best_pos / pos_trend / pos_vs_ninki、kako5_same_cond_best_pos、hist_same_cond_best_pos / top3_rate / count、hist_same_place_best_pos、horse_fuku10/30、kako5_expected/upset/hidden_good_count など 24 本。クラス名も入る。
- これらの gain の合計は、**v6 で 51.6%（kako5_avg_pos 13.2%、前走確定着順 12.3% が 1・2 位）、v8 で 5.1%**。v8 は JRDB 前日 KYI（`k8_*` 41 本）が 71.1%（k8_jk_idx_z 39.8%、k8_jk_idx 18.8%）、JRDB 過去走（`j1_*` 59 本）が 7.5%。
- JRDB の IDM（`k8_idm`、`j1_idm_*`）も「能力の 1 次元表現」だが、走破タイムから作る指数で、Elo（着順と相手関係）とは作り方が違う。

### A3. 情報源をどれくらい共有しているか

| | PW | v6 | v7 | v8 |
|---|---|---|---|---|
| 過去の着順 | ◎（唯一の入力） | ◎（gain 52%） | ○ | △（gain 5%） |
| 相手関係（誰に勝ったか）の伝播 | ◎ | ×（クラス名だけ） | × | ×（IDM は時計ベース） |
| 走破タイム・上がり・通過 | × | ○ | ○ | ○ |
| JRDB | × | × | 過去走 59 列 | 過去走 + 前日 KYI（71%） |
| オッズ・人気 | × | 前走人気のみ | 同左 | 同左 |
| 記憶の長さ | 長い（K が 32 まで下がり、1 走で大きく動かない） | 近 5 走中心 | 同左 | 同左 |

**整理**: PW がモデルと独立なのは「相手関係の集約」と「記憶の長さ」の部分だけで、生の材料（着順）は同じ。
過去に Elo 4 アームと Glicko-2 を v6 の特徴として足した実験では、全レースの予測ゲート（ΔAUC ≥ +0.008 かつ Δpairwise ≥ +0.005）で LOSE/REDUNDANT だった（`docs/research/NEXT_GEN_RESEARCH_PLAN_20260918.md` §B-1、`reports/race_elo_exp.json`）。
「平均ではほぼ冗長、でもモデルと割れた馬に限ると差が出る」という形で、D3' の結果と矛盾しない。ただし §B4 のとおり、その差は市場がすでに織り込んでいる。

## D. 前向き確認の前提

### 保存に必要な追加処理（提案。実装はまだしない）

1. **Phase A で PW の凍結ファイルを作る**: `Invoke-PowerRating` の `build --until {date}` の直後に、その週の全出走馬について `reports/zure_freeze/{date}.json` を書く。中身:
   - race_id・馬番・馬名・芝ダ
   - PW のレーティング生値 R と、その時点のスケールでの点
   - 出走表の中での順位、単独 1 位かどうか、1 位と 2 位の差
   - モデル順位と bundle の sha256、モデル世代
   - 馬レベル・スピード指数の順位（D1/D4 の弱層用）
   - `power_rating` のパラメータ（k0・floor_ratio・tau）、入力データの最終日、コードの git sha、作成時刻
2. **発走前に固定する**: `bundle_provenance.py` と同じく、最初の発走前に書き、発走後は書き換えない。ハッシュを manifest に残し、最初の発走前に commit する（後から作り直していないことの証拠）。
3. **日曜分の扱いを決める**: Phase A は土曜朝に土曜の日付まで作るので、日曜の PW には土曜の結果が入らない（同じ週末に 2 回走る馬はまれ）。土曜朝の版で固定するか、日曜朝にもう一度固定するかを、数え始める前に仕様書に書く。
4. **発売前取消の扱い**: 凍結時点の出走表で順位を付け、判定時は今回と同じく、発売前取消の馬を除いて付け直す（両方を残す）。
5. **SHAP も同時に残す**（C8 の代わり）: `export_weekly_marks.py` で LightGBM の `predict(pred_contrib=True)` を 1 回呼び、D3' 候補（PW 単独 1 位 × AI 6 位以下）の馬の寄与上位をこのファイルに入れる。v8 で「何が順位を下げたか」が前向きに分かる。
6. **前向き確認の判定は、人気をそろえた比較も事前に決める**: B4 のとおり、モデル順位だけの対照では「市場がすでに知っていること」でも lift が出る。強層の意味（当たる信号なのか、市場を超えるのか）に合わせて、「人気（または T-10 オッズ）をそろえた対照」での判定を加えるかを、数え始める前に決めるのがよい。
