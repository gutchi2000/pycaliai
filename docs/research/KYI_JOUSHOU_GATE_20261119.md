# v8 の 11/14 作り直しが品質ゲートで止まる件（k8_joushou 84%→0%）の原因と修正（2026-11-19）

## 1. 結論

- **値は消えていない。ゲートの測り方の誤判定。**
  - 11/14 の KYI では、上昇度が入っている馬が全頭「3」だった。
  - 品質ゲートの充足の測り方（`export_weekly_marks.feature_coverage`）は「全頭同じ値なら情報ゼロ＝0%」と数える。そのため 86% 入っている列を 0% と判定し、「無言死」としてゲートを落とした。
  - 結合キー・列名・型・日付・絞り込みは、どれも正常だった。
- **11/21 でも起こりうる。**
  - 上昇度は値の約 89% が 3 で、3 以外の馬は 1 日に 0〜10 頭しかいない。
  - 配信したレースで全頭 3 になった日は、2026 年 63 開催日のうち 4 日（07-05、10-25、10-31、11-14）。直近 8 開催日（10/24〜11/15）のうち 3 日がそうだった。
- **起きたときの挙動**: Phase A は止まらず、その日だけ v7 で bundle を作り直す（`weekly_nicegui.ps1` の戻り先）。v8 本番の初日に v8 が使われなくなるところだった。
- **修正（master 56954ada）**: `CONST_OK_COLS` に `k8_joushou` を足し、この列だけ「全頭同じ値」を正常として埋まり率で測る。
  - 予測は変わらない。11/14・11/15 を作り直すと、bundle の中身はレース・馬・確率・印まで修正前と完全一致した（違いは `serve_path.git.commit` だけ）。
  - 11/14 はゲートを通るようになった（無言死 0、rc=0）。
- 他の KYI の列（28 列）で、全頭同じ値になった日は 2026 年に一度もない。直したのはこの 1 列だけ。

| 段 | 11/14 | 11/15 |

- 11/14 の本番配信は v7（k8_* を使わない）だったので、当日は表に出なかった。

## 3. どれくらい起きるか

- 上昇度の値の分布（`kyi.parquet`、年ごと）は、2013〜2026 年でほぼ同じ。3 が 87〜89%、5 が 1〜4%、2 が 0.2% 前後、残りは空欄。
  - 5 は年々減っている（2013 年 3.5% → 2026 年 0.9%）。全頭 3 の日は、これから増える方向。
- 2026 年の KYI ファイル 97 本のうち、全頭 3 の日は 4 本（03-08、10-25、10-31、11-14）。
- 配信したレースに絞ると 63 日中 4 日。3 以外が 1 頭だけの日も 5 日あった。
- 学習（2013〜2025）でも同じ分布なので、全頭 3 の日の入力は学習と同じ種類の値。配信の劣化ではない。

## 4. 修正の中身と影響範囲

`export_weekly_marks.py` の `CONST_OK_COLS` に `"k8_joushou"` を足した（理由はコメントに記載）。

- この集合を使うのは次の 4 か所で、どれも測るだけ。予測の計算・bundle の中身・買い目には触れない。
  1. 品質ゲートの無言死判定
  2. 学習比の劣化の警告（絶対 canary）
  3. 死んだ特徴の gain 合計
  4. `analysis/measure_serve_coverage.py` の基準づくり
- 検出力:
  - 未取得や解析失敗で上昇度が空になった場合は、非欠損率が下がるので、今まで通りゲートで止まる。
  - 「別の列の値が中央値で埋められて全頭同じ」という、定数ルールが本来狙っている事故は、この列では起こらない。KYI の素の値をそのまま入れているだけで、中央値で埋める処理を通らない。
- 基準（`data/serve_feature_baseline.json` の k8_joushou 84%）は作り直さなくてよい。作り直すと 86% 前後になるだけ。

## 5. 金曜夜の確認方法（Phase A の前と後）

**前**: 金曜 19:40 の `PyCaLiAI_JRDB_Snapshot` で 11/21 の KYI が保存された後に、次を実行する。

```
python scripts/kyi_precheck.py 20261121
```

- 1 行目に使う KYI の控え（`KYI261121__20261120T1940xx.zip`）と行数が出る。「KYI が無い」と出たら、v8 は使えず v7 で作られる。
- `KYI の IDM の埋まり` が 90% 以上であること。下回ると export が v8 を諦める。
- 列ごとの表の「ゲート」欄が、「基準」欄と同じくらいであること。「← 止まる」の印が付いた列があれば、ゲートで止まる。
- 最後の行が `[通る見込み]` なら、KYI 由来の列は通る（exit code 0）。
- Phase A の後に実行すると、配信したレースだけで測り直す。

**後**: `logs/export_20261121.log` で次を見る。

- `[kyi] 前日 KYI KYI261121__… 埋まり 100%`。90% 未満は v8 を諦める。
- `[serve canary] 監視 N 特徴 / 無言死 0`。0 以外なら、直後の `serve特徴が無言死 (…)` に止めた列が出る。
- `品質ゲート不合格` の行が無いこと。
- Phase A の出力に `today's bundle was built with v7 (fallback)` が無いこと。`logs/export_20261121_v8.failed.log` があれば、v8 が落ちて v7 で作り直している。
- `reports/cowork_input/20261121_bundle.json` の `"model": "v8"`。

## 6. 残ること

- 同じ形の誤判定は、もともとほとんど 1 種類の値しか取らない列なら、他の列でも起こりうる。今回調べた KYI の残り 28 列では起きていない（2026 年に全頭同じ値の日は 0）。外厩の列は調べていない。
  - j1_*（過去走）は、IDM の列で測る（`coverage_series`）ので対象外。
- 上昇度そのものの情報量は小さい（ほぼ 3）。特徴として残すかどうかは、今回の範囲外。
